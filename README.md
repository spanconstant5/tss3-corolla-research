## What This Project Is

Toyota's TSS 3.0 (Toyota Safety Sense 3.0) vehicles use SecOC (Secure Onboard Communication) to authenticate CAN messages. The EPS (Electric Power Steering) module rejects unsigned steering and braking commands. This makes third-party ADAS software like [openpilot](https://github.com/commaai/openpilot) unable to control the vehicle without a way to produce valid message authentication codes (MACs).

The approach being pursued (originated by [kaikozlov](https://github.com/kaikozlov)) uses the EPS itself as a signing oracle: a small RAM-resident program is loaded into the EPS's volatile memory via the UDS (Unified Diagnostic Services) programming interface. This resident program intercepts control requests on a dedicated CAN mailbox (0x777), signs them using the EPS's own cryptographic engine, and emits signed responses on 0x7A9. The host (openpilot on a comma device) sends unsigned commands to 0x777 and receives back signed frames ready for CAN bus injection.

The oracle kit was originally built and tested on a **2026 Toyota Camry Hybrid** (`8965F3307000`). This research is about porting it to the **2025 Toyota Corolla Hybrid** (`8965F1208000`), which uses different firmware with different internal memory layouts, function addresses, and contract resolution targets.

## Research Timeline

### Phase 1: CAN Bus Architecture Analysis (Aug–Sep 2026)

Established the Corolla's CAN topology from the panda's perspective:

- **Bus 0**: Powertrain CAN (PT CAN) — 22 message IDs, ~1182 frames/sec observed. This is where 0x160 (32-byte CAN-FD ADAS command from camera) and 0x08A (32-byte SecOC-signed combined lateral+longitudinal control) live in normal operation.
- **Bus 1**: EPS diagnostic bus — very low traffic (2 IDs, 5 frames observed in preflight). **This is where the EPS answers UDS diagnostics** at physical addresses TX 0x7A1 / RX 0x7A9. Confirmed by TSK preflight probe (see below).
- **Bus 2**: Camera CAN — mirrors bus 0 traffic (22 IDs, ~1182 frames/sec). The comma harness taps between camera and gateway.

Key finding: **ECUs return zero UDS responses on the "tapped" buses** during normal openpilot fingerprinting. The fingerprint file for this car notes FW_VERSIONS is empty because standard FW queries get no response on bus 0 or bus 2. UDS diagnostic access requires bus 1 with ELM327 param 1 (harness mode, not OBD).

### Phase 2: EPS Firmware Acquisition (Aug 2026)

### Phase 3: Placebo Discovery and 0x160 Dead End (Sep 2026)

A critical finding that redirected the entire project:

The user's existing openpilot branch ("2023", commit 683bbcc) appeared to provide longitudinal control via 0x160 frame injection. Quantitative analysis proved this was **placebo**: during 2842 divergence samples where OP's transmitted 0x160 differed from the camera's by |Δaccel| > 0.3 m/s², regression showed the car followed the camera (β=0.78, corr=0.93) not OP (β=0.18, corr=0.77). The original branch author confirmed: "all I ever got was op controlling the toggle. Braking, accelerating and steering was TSS all along."

**Why 0x160 injection fails for braking**: OP's `modify_tss3_160` rewrites only ACCEL_REQ (bytes 4–5), counter (byte 2), and E2E CRC (bytes 0–1) in the camera's 0x160 template. Bytes 8–23 contain camera-internal state (byte 12 correlates with decel, bytes 21–23 are brake-mode flags) that cannot be synthesized from commanded acceleration alone (ML model: 15% exact accuracy, worse than baseline). When OP wants to brake but the camera is coasting, the frame is internally inconsistent → PCM follows the coast bytes → no braking.

**Deeper reason 0x160 is a dead end**: The real actuation command is 0x08A (`STEER_ANGLE_ACC_STATUS`), a 32-byte SecOC-signed message on powertrain bus 1. 0x160 is only the camera's ADAS *request* that gets translated downstream; 0x08A is the actual signed command the EPS and braking system obey (corr 0.90 with aEgo when ACC engaged). Without SecOC signing capability, OP cannot produce valid 0x08A frames.

This confirmed the oracle/signer approach is the only viable path to real vehicle control.

### Phase 4: Panda Safety Model Analysis (Sep 2026)

The StarPilot panda firmware (`DEV-75aa44be-DEBUG`) was analyzed to understand why lateral control (steering) also didn't work:

- The binary selects `TOYOTA_SECOC_LONG_TX_MSGS` for TSS3 vehicles
- This TX allowlist has **no 0x160 entry** at bus 0, length 32 — openpilot's 32-byte 0x160 injection is silently blocked by `safety_tx_hook`
- Simultaneously, the camera's original 0x160 IS forwarded from bus 2 to bus 0 unmodified (no relay-check entry blocks it)
- **Two simultaneous failures**: TX blocked (OP can't inject) + relay not blocked (camera's frame passes through)
- Fix requires panda firmware with TSS3-specific safety mode: `{0x160, 0, 32, .check_relay = true}`

### Phase 5: openpilot Integration Architecture (Sep 2026)

Mapped how Kai's `tss3` branch implements real control:

**The oracle signing flow**:
1. openpilot builds an unsigned 28-byte 0x08A application payload (lateral angle, longitudinal accel, sequence number, request IDs)
2. Sends it to the EPS oracle via 0x777 — 6 frames × 5-byte fragments, functional-nibble4 codec
3. EPS oracle responds on 0x7A9 with the 4-byte MAC signature
4. openpilot appends MAC → publishes signed 32-byte 0x08A on downstream bus 0
5. 100 Hz loop with 90 ms publication deadline, fail-closed

**Camry-hardcoded issues found in `tss3` branch** (all fixed on `tss3-expand`):
- `EXPECTED_ORACLE_TARGET = "camry-8965F3307000"` — rejected non-Camry kits
- Catch marker hardcoded `"target": "TOYOTA_CAMRY_TSS3"`
- Topology hardcoded `--topology camry-post-repin`
- CAN-FD auto-promotion bug killed EPS diagnostic responses during fingerprinting

**Integration points for Corolla enablement**:
- `developer.py`: UI gate for oracle bringup button (currently `exact_f33 = CP.carFingerprint == CAR.TOYOTA_CAMRY_TSS3`)
- `tss3_oracle.py`: Tool path and oracle lifecycle management
- `tss3.py`: Transport layer, request plane, bus mapping

### Phase 6: Corolla Signer Payload Build (Oct 2026)

Successfully cross-compiled the Corolla-specific signer payload on Windows using Kai's `ghidra_rh850` build system.

**Build environment challenges solved**:

1. **Windows Docker quoting**: Python's `subprocess.run()` with list arguments on Windows produces incorrect quoting for Docker `-v` mount paths. Fix: switched to `--mount type=bind,source=...,target=...` syntax.

2. **Python 3.12+ tempdir ACLs (CVE-2024-4030)**: `tempfile.TemporaryDirectory` creates directories with restrictive EXPLICIT ACLs that block Docker's file sharing layer. Error manifests as "Access is denied" from Docker daemon. Fix: run `icacls <tempdir> /grant "Everyone:(OI)(CI)F"` immediately after temp directory creation.

3. **Windows path separators**: `Path.relative_to()` returns backslashes on Windows; these end up in `#include` directives inside the Docker Linux container. Fix: `.as_posix()` on the relative path before string formatting.

4. **Build script approach**: Changed from inline `sh -ec '<script>'` to writing build commands to `_build.sh` file and running `sh -e /out/_build.sh` to avoid shell escaping issues across the Windows → Docker boundary.

**Build output** (target `corolla-8965F1208000`):
- Payload SHA256: `72ffc3eebbec7966177c700a12e3d132f4a5bd03682e61f266bfea62815f8122`
- Payload size: 4096 bytes (4 KB)
- Compatible targets: `corolla-8965F1208000`, `corolla-8965H1202000`
- Signer protocol: 0x777 request → 0x7A9 response, bus 1, four-frame functional-nibble4 codec

### Phase 7: Install Attempt and Bus Routing Investigation (Oct 2026)

Payload and metadata deployed to comma device at `/data/tss3-oracle/bundle/`. The `doctor` subcommand validates both files successfully. However, `install` fails: **F181 (Application Software Identification) read returns None**.

**The F181 failure chain**:
1. `install()` loads metadata → `meta_transport()` extracts bus=1 from JSON config
2. Creates UDS route: `explicit_route(bus=1, elm327_param=1, uds_variant="old")`
3. `execute_ram_payload()` creates UDS client at TX=0x7A1, RX=0x7A9 on bus 1
4. Attempts `diagnostic_session_control(DEFAULT)` then `read_data_by_identifier(F181)`
5. UDS read times out → returns `(None, None)` → raises "F181 mismatch: expected ..., observed None"

**Why it worked before but doesn't now**:

The TSK firmware dump (Phase 2) successfully used the **same** bus 1, param 1, addresses 0x7A1/0x7A9 — but with:
- **Different panda**: The TSK session used a dedicated diagnostic panda, not the user's daily-driver panda
- **Different harness status**: TSK session had `harness_status: 2` (flipped); user's current harness status is unknown but may be `harness_status: 1` (normal)
- **Different safety mode context**: TSK runs its own diagnostic safety configuration; the signer installer uses `ELM327_SAFETY_MODE=3` with param 1

**The harness orientation hypothesis**: The comma harness connector can be plugged in two orientations. "Flipped" (status 2) vs "normal" (status 1) swaps the mapping between physical CAN buses and panda logical buses. If the TSK session used a flipped harness and the current setup uses a normal harness, the EPS (physically on one CAN bus) would appear on a *different* panda logical bus. The install sends diagnostics to logical bus 1 but the EPS may now be on logical bus 0.

**Immediate next step**: Try the install with bus=0 in the metadata JSON, or verify harness orientation matches the TSK preflight's `harness_status: 2`.

## 0x08A Control Message Structure

The combined lateral + longitudinal control message (`TSS3_CONTROL_REQUEST`, CAN ID 0x08A):
- 28-byte unsigned application payload + 4-byte SecOC MAC trailer = 32 bytes total
- Fields: LATERAL_REQUEST_PINION_ANGLE, LATERAL_REQUEST_ID (11=LTA, 0=off), LATERAL_ASSIST_GAIN (100 or 50), LONGITUDINAL_REQUEST_ACCEL (int16 at bytes 8–9, mirrored 11–12; corr +0.90 with achieved aEgo), SET_SPEED, REQUEST_SEQUENCE (u6)
- On the Corolla, the oracle signs this via command-5 presecoc backend
- Corolla backend currently implements **lateral only** (target angle via 0x0B6 lateral ID); full combined longitudinal signing is Camry-demonstrated but not yet extended to Corolla

## Repin Requirement

Real vehicle control requires the panda to be **in-line** on the powertrain CAN bus (bus 1), not just tapping it. This is called a "repin" — physically rewiring the comma harness so the panda relay can:
1. Inject signed 0x08A frames onto the powertrain bus
2. Suppress the stock producer's conflicting frames (co-transmission does not work; the stock producer must be silenced)

Without repin, the panda can observe bus 1 traffic and perform UDS diagnostics, but cannot inject actuation commands. The EPS diagnostic/oracle path (0x777/0x7A9) works without repin because it uses a dedicated diagnostic mailbox, not the main CAN bus traffic flow.

Software-based suppression via UDS CommunicationControl (0x28) is theoretically possible but the ACC producer ECU and suppression point on the Corolla have not been identified.

## Steering-Specific Notes (LTA)

Lateral control via 0x160 template modification requires the stock LTA (Lane Tracing Assist) to be enabled on the dashboard. The `modify_tss3_160` function only overwrites accel, steer angle, counter, and CRC — the LTA enable/mode bits pass through from the camera's template. With LTA off, the template carries "LTA inactive" and the EPS ignores the steering angle bytes.

The specific LTA-enable bit position within the 32-byte 0x160 frame is **unidentified**. The DBC has raw BYTE00–BYTE31 with no named LTA signal. Identifying this bit requires either a parked CAN capture while toggling stock LTA on/off, or reverse engineering the EPS CodeFlash in Ghidra to find which 0x160 bits gate steering actuation.

## Open Questions

1. **F181 None on install**: Is this a harness orientation issue (flipped vs normal), a panda-specific issue, or something else? The TSK preflight proves bus 1 / param 1 works with harness_status=2.
2. **Longitudinal signing on Corolla**: The command-5 backend currently handles only lateral (0x0B6). Extending to combined 0x08A longitudinal fields needs implementation.
3. **ACC producer identification**: Which ECU produces the stock longitudinal commands, and can it be silenced via software (UDS 0x28) or does physical repin remain required?
4. **LTA enable bit**: What bit(s) in the 0x160 frame gate EPS lateral actuation? Needed for steering without stock LTA enabled.
5. **SecOC key validation**: The oracle path bypasses key knowledge (EPS signs for you), but the existing SecOC signing code in openpilot (`carcontroller.py` `add_mac`/`build_sync_mac`) has not been verified against this car's keys.
